# TRIDENT 统一安全 Agent 执行方案 v2.0

- 日期：2026-11-12
- 状态：按用户最新产品目标重建的执行基线；尚未实现的能力均为开发目标，不代表已经交付。
- 产品名称：**TRIDENT**。
- 工程根目录：`E:\pentest agent\TRIDENT\`。
- 当前方案权威入口：本文。旧“三角融合、Commander / Operator / Auditor”平台方案废止，旧 P0—P6 不再作为开发顺序。
- 核心原则：**一个统一 Agent、四项业务能力、事实与证据驱动、修复可回退、验证可复核、安全边界由代码与运行时落实**。

> **产品定义：吸收 Sapper、ARTEX、CodeScan 的优点，开发一个具有“软件供应链安全分析、源代码审计、AI 辅助漏洞挖掘、漏洞自动化修复与补丁生成”能力的全新 Agent。不是运行、包装或调度三个原项目的平台。**

## 1. 产品目标与成功标准

### 1.1 用户实际获得什么

用户提供源码仓库、依赖资料及任务要求，TRIDENT 在许可范围内自主推进分析，交付：

1. 项目结构、分析范围、依赖清单和可追溯的软件物料清单。
2. 具有源码、依赖路径或测试证据的安全问题，而不是只有模型猜测的漏洞列表。
3. 对候选漏洞的验证过程、成立条件、反证和无法确认的部分。
4. 与具体问题关联的最小修复补丁、回归测试和依赖升级建议。
5. 修复前后对照验证结果、残余风险、测试限制和可审查报告。

成功闭环：

**理解项目 → 识别风险 → 提出假设 → 获取证据 → 确认或排除 → 生成补丁 → 验证修复 → 交付。**

### 1.2 不再采用的产品形态

- 不把三个上游项目作为三个可运行产品托管。
- 不以 Commander / Operator / Auditor 三个自主角色作为核心架构。
- 不把“派发 Mission、Worker 抢领、跨角色交接”作为新 Agent 的业务主循环。
- 不把完成数据库治理平台、复杂资源池或多租户管理作为实现新 Agent 的前提。
- 不以接入工具数量、运行任务数量或 Agent 能聊天作为产品完成标准。

### 1.3 首版范围

首版聚焦 **Java Web 应用，优先 Maven、Spring MVC / Spring Boot 和常见 Spring Security 配置**，跑通四项核心能力的纵向闭环。

Java 是第一批支持对象，不是永久语言限制。Gradle、其他 Java 框架和其他语言按样本覆盖扩展，不能因“能读取文件”宣称支持完整审计。

## 2. 从三个项目吸收什么

| 来源 | 吸收的优点 | 在 TRIDENT 中的落点 | 不直接继承 |
|---|---|---|---|
| Sapper | 目标驱动、探索方向、预算意识、停泊与收敛、上下文连续性 | 统一 Agent 的任务计划、假设队列、进展检测与上下文摘要 | 外部 commander/watchdog 产品编排、文件状态作为第二权威源 |
| ARTEX | 结构化事实、关系追踪、工具调用记录、事件与结果追溯 | Evidence / Finding / Patch / Validation 关联、运行事件和工具记录 | 为实现三角色而设计的强制分工和 Mission 交接链 |
| CodeScan | 项目与依赖识别、Java 依赖读取、源码定位、接口权限分析思路 | 项目索引、供应链分析、源码审计和代码上下文工具 | 任意源码写权限、过大的工具集、未经验证的全路径审计承诺 |

复用规则：

1. 优先复用有测试、可隔离、边界清楚的功能；机制借鉴与源码复制分别记录。
2. ARTEX / CodeScan 的现有源码许可为 AGPL-3.0，直接复制、修改、分发或网络提供服务前，必须审查对应义务，不自行替用户决定产品许可。
3. `sapper-v18-mixed` 在本机是 OCI 镜像导出，不是展开的源码仓库；若提取应用源码，须核对文件来源和实际许可，不能把“可读镜像层”当成已完成可复用移植。
4. Java 依赖扫描、POM 解析和反编译基础不等于完整 AST、调用图和污点分析引擎，复用后仍需独立验收。
5. 三个上游目录只作参考，不在本次文档替换中修改或删除。

## 3. 总体架构：一个 Agent，多项受控能力

### 3.1 架构组成

- **TRIDENT Agent Core**：唯一的自主任务理解与决策入口，维护一个 Run 的逻辑上下文、计划、假设和进度。
- **Model Adapter**：封装模型请求、工具调用、流式响应、错误与用量；同一 Run 记录实际模型和配置。
- **Tool Registry + Policy**：结构化工具定义、参数校验、授权检查、预算检查和阶段能力开关。
- **Project / SCA / Audit / Validation / Patch 能力模块**：被 Agent 调用的普通代码与分析工具，不是各自拥有自主目标的 Agent。
- **Workspace Manager + Sandbox Runner**：提供不可变输入、隔离工作副本、受控测试与资源限制。
- **Result Store + Artifact Store**：保存权威运行状态、结构化结果、证据与补丁。
- **CLI / Report**：首版用户入口和交付出口；UI 后置。

### 3.2 统一不意味着无限权限

同一个 Agent 可依任务阶段获得不同工具，但权限由代码和运行环境切换：

| 阶段 | 主要能力 | 写入边界 | 执行与网络 |
|---|---|---|---|
| 分析 | 项目发现、源码检索、依赖、AST、路径分析 | 原始源码只读，仅写结果 | 默认不执行项目代码；分析工具默认无目标网络 |
| 漏洞验证 | 生成测试、调用固定验证配方 | 验证工作副本 | 独立沙箱；默认无公网出口 |
| 修复 | 生成/应用最小补丁、增加测试 | 仅修复工作副本及允许文件 | 不获得任意 Shell，不自动推送 |
| 修复验证 | 编译、测试、安全回归、差异检查 | 临时验证副本 | 受控命令、资源上限、固定依赖与网络策略 |
| 交付 | 导出报告、SBOM、Diff 和证据索引 | 输出目录 | 不自动修改原仓库、合并、发布或部署 |

阶段只是能力状态，不是 Commander / Operator / Auditor 的改名。

### 3.3 并发边界

解析文件、计算索引和运行互不冲突的分析器可以并行。它们是确定性工具任务，不必具备独立模型、记忆或派发权限。首版不引入自主子 Agent 网络；确需扩展时另行评估，不能悄悄恢复三角色平台路线。

## 4. 统一 Agent 的决策循环

### 4.1 运行流程

1. 验证输入项目、操作许可、允许路径、数据外发与预算配置。
2. 固定源码快照和依赖/情报版本，创建 Run。
3. 调用项目识别工具，形成项目地图和初始上下文。
4. Agent 建立可更新的计划与漏洞假设，选择当前允许的工具。
5. 工具执行前由策略代码校验；执行后保存结构化结果和 Artifact 引用。
6. Agent 根据新事实继续检索、追踪路径、请求验证、修订或排除假设。
7. 证据达到标准后形成 Finding，进入修复或人工复核。
8. 在独立副本生成补丁和回归测试，调用受控验证工具。
9. 失败时分析原因、有限次修订，或交付未验证补丁与限制，不能伪报成功。
10. 达到完成、预算、停止或不再有进展条件时生成报告并安全结束。

### 4.2 Agent 必须是真正的智能体

- 可以依据新证据调整分析方向，跨文件追踪调用关系，决定下一项工具操作。
- 不是“按固定顺序跑扫描器，最后让模型写摘要”。
- 也不是只给模型预生成的调度 candidate ID，让它不能理解或修改分析计划。
- 工具名称、参数结构、可访问路径、执行配方、外发权限和预算仍受确定性代码约束。
- 找不到证据、符号无法解析或验证环境不足时，记录“无法确认”，不得自行补造调用链。

### 4.3 模型接入要求

首版沿用 Go 主工程，通过一个薄 Model Adapter 接入正式模型 API；不为模型选择另造通用编排平台。

- 使用所选服务商的正式 SDK；具体 SDK 版本在接入时依据文档和编译测试固定。
- 模型、服务地址、超时、调用上限和数据策略通过配置设置，不能写死在审计业务逻辑中。
- 工具结果应结构化、有大小限制并可分页；过大文件按范围检索，不能静默截断后声称完整审计。
- 正确处理工具调用、正常结束、截断、拒绝、限流、超时、取消和用量计量。
- 重试模型请求与重放有副作用工具操作分开处理。不能因为网络重试而重复应用补丁或执行测试。
- 单测可用 Fake Model 检验协议，但阶段验收必须有经过用户数据外发许可的真实模型工具调用闭环，不能用假模型冒充新 Agent 已接入。
- 本文不替用户购买服务、配置凭据或发送源码；模型供应商/部署方式不构成产品架构绑定。

### 4.4 上下文与恢复

上下文分为：任务约束、项目地图、近期工具结果、已验证事实、活跃假设、Finding 与补丁摘要、未完成事项。

大段源码、日志和依赖公告通过受限检索按需读取，摘要附来源；恢复时从持久 Run 和 Artifact 重建，而不是仅依赖一份自由文本 STATE。

## 5. 工作区与输入完整性

### 5.1 输入

首版支持本地源码目录及明确版本的仓库快照；远程拉取后续通过受限获取组件实现。记录：项目来源、Commit（如有）、文件清单、内容 Hash、导入策略、排除范围和工具版本。

必须处理路径穿越、符号链接/Windows junction 或 reparse point 越界、归档炸弹、特殊文件、超大文件、恶意编码和子模块来源。默认不读取 `.env`、私钥、凭据目录等敏感文件，必要访问需单独许可。

### 5.2 三种目录

1. **Source Snapshot**：不可变分析基线，不承接补丁写入。
2. **Patch Workspace**：从明确 Snapshot 创建的独立可写副本，补丁限定在此。
3. **Validation Workspace**：针对基线或某个 Patch Hash 构建的隔离临时副本，允许测试产物，不污染分析基线。

用户原目录不作为测试输出或修复临时目录。导入后源目录发生变化，不得把旧证据自动关联到新文件；重新导入生成新快照。

### 5.3 仓库内容不可信

README、注释、构建文件、测试名称及扫描器输出都只是数据，不能修改系统策略、授权、工具集或外发地址。编译器、解析器、测试运行器本身也应有资源限制；“没有执行应用主函数”不代表处理恶意仓库没有风险。

## 6. 软件供应链安全分析

### 6.1 首版必做

- Maven 项目、模块、源码根目录及依赖声明识别。
- 依赖坐标、版本、作用域、直接/传递关系、解析依据和包 Hash（可获得时）。
- 固定版本漏洞情报的版本区间匹配、别名去重、来源及获取时间记录。
- 漏洞组件的调用点、外部输入路径和运行条件分析。
- 输出 SBOM、依赖风险清单、推荐升级版本及兼容性验证结果。

### 6.2 不执行构建也要诚实表达解析能力

仅解析 `pom.xml` 不能保证得到 Maven 的真实有效依赖树。属性继承、BOM、dependencyManagement、profile、版本范围和冲突仲裁必须分别处理。

推荐顺序：

1. 读取声明、已存在的锁定/解析报告、已批准本地缓存与制品元数据。
2. 静态可解的模块与依赖建立图，未解析项明确标记。
3. 如需执行 Maven 解析有效依赖，必须使用单独获批的解析配方和沙箱，记录 profile、JDK、配置及仓库来源；不能在宿主机隐式运行仓库 wrapper、插件或任意脚本。
4. Gradle 首版可以识别文件并报告 partial；没有可信解析结果时不能静态猜测成完整依赖图。

### 6.3 供应链结论分层

| 状态 | 含义 |
|---|---|
| version_matched | 版本落入公告影响区间，只是候选风险 |
| callsite_found | 项目存在相关组件/符号调用点 |
| input_reachable | 有证据说明外部输入可达相关调用路径 |
| runtime_confirmed | 隔离环境验证对应触发与安全影响 |
| not_affected | 有明确排除依据，记录版本、配置与适用条件 |
| unknown / partial | 资料、解析或路径覆盖不足，无法确认 |

未发现调用点不等于不可达。反射、框架装配、动态加载和缺失源码必须计入限制。

### 6.4 扩展能力

依赖来源异常、Hash 不符、可疑安装/构建行为、拼写相似和许可证风险可形成单独风险项，但不能凭一个指标认定恶意包或合规违法。完整恶意包检测、跨生态制品溯源不是首版承诺。

## 7. 源代码审计与 AI 辅助漏洞挖掘

### 7.1 第一批分析器

- Java AST：优先 JavaParser，作为独立可限额运行的分析工具，Go 侧通过结构化 JSON 接口调用；准确版本在实现时固定。
- 入口：Spring MVC 注解路由、参数绑定，Servlet 后续纳入固定样本。
- 权限：声明注解、可见安全配置、过滤器/拦截器、对象访问检查及其覆盖条件。
- 数据流：方法内 Source / Sink / Sanitizer，加有界跨方法追踪；记录深度、未解析符号和动态调用。
- 配置与依赖规则：读取明确支持的配置文件、已批准情报与规则包。

不能只依赖正则匹配就宣称具备跨文件安全语义分析；模型解释也不能替代代码位置和路径证据。

### 7.2 风险覆盖

优先关注：SQL 注入、命令注入/RCE、SSRF、路径遍历与任意文件访问、危险上传、XSS、反序列化、认证/权限绕过、敏感信息泄露和不安全配置。

**优先级不等于首版自动修复覆盖。** 第一轮针对少量规则形成正例、负例与边界例，再扩展类别。

### 7.3 假设驱动挖掘

每条假设记录：入口、攻击者可控输入、期望安全约束、潜在危险操作、路径、缺失证据和下一项验证。

Agent 应能：

1. 从框架、权限与业务代码发现自动规则未覆盖的风险假设。
2. 跟进跨文件调用、校验函数、身份上下文和依赖实现。
3. 发现防护或反例后主动反驳、降低置信度或关闭假设。
4. 为高价值假设生成测试，优先本地函数/集成级验证，不转向无关互联网扫描。
5. 将静态漏洞、可疑设计与实际安全影响分开。

## 8. 漏洞验证与结果等级

### 8.1 Finding 模型

每项 Finding 至少包含：ID、类别/CWE（适用时）、高/中/低危、位置、根因、影响与前提、静态/运行时状态、证据引用、分析限制、规则/模型版本及修复关联。

验证状态与严重程度、风险处置分开：

- candidate：待验证线索。
- static_confirmed：可复核静态链成立，不宣称运行时已利用。
- runtime_confirmed：受控测试证明指定环境下的安全影响。
- refuted：反证说明当前假设不成立。
- inconclusive：缺环境、权限或证据，无法确认。

### 8.2 验证配方

首版使用明确配置的测试配方，不开放任意 Shell。每个配方声明：可执行程序、参数 Schema、工作目录、允许文件、依赖集合、超时、CPU/内存/进程上限、网络与输出限制。

仓库中的 Maven/Gradle 脚本、测试和插件是非可信代码。原有测试不能因为“来自用户项目”就直接在宿主机执行。

### 8.3 环境隔离

- 无宿主机敏感挂载，无 Docker Socket、SSH Agent、云凭据或模型 API 密钥。
- 容器低权限、资源受限，测试服务在专属网络内；默认无公网出口。
- 如必须获取依赖，使用独立受控获取步骤、指定仓库和固定 Hash/版本，不向测试容器注入任意联网权限。
- 授权本地 HTTP 复现仅用于隔离测试实例，不能自动扩展到生产或互联网目标。
- 取消任务时实际终止受控进程并记录结果，而不是仅修改状态字段。

## 9. 自动化修复与补丁生成

### 9.1 修复流水线

1. 选定具有足够根因证据的 Finding，确认可写文件与修复范围。
2. 创建固定基线的 Patch Workspace，记录源码和依赖状态。
3. 生成 FixPlan：根因、修复策略、修改文件、兼容性风险、验证方法和回退方式。
4. Agent 在允许路径中应用小粒度变更并生成回归测试。
5. 计算 Patch Hash，生成统一 Diff，检查越界、凭据、额外文件及异常大改动。
6. 在前后验证前冻结同一套安全回归测试及必要业务测试，记录 TestSuite Hash；将新增测试以相同内容装配到基线和补丁验证副本，不以“基线没有该测试”为由省略对照。
7. 对原始基线运行冻结测试，确认失败原因确实是目标漏洞；对同环境中的补丁版本运行同一 TestSuite，记录实际执行数、跳过数、日志和退出码。
8. 由确定性验证门禁判断结果：只有基线失败确因目标漏洞、补丁相同安全测试通过、必要业务回归实际执行且无退化、证据完整时才允许标记 validated。零测试、必需用例跳过、编译失败、超时或缺证据都不能通过；不能只依赖模型判断或退出码0。对补丁重新分析，确认没有只遮蔽现象或引入明显新风险。
9. 输出补丁、验证报告和限制；用户另行批准才应用到原项目或提交。

### 9.2 第一批可自动修复类型

| 类型 | 首批允许的修复范围 | 不自动承诺 |
|---|---|---|
| SQL 注入 | 明确可解析的 JDBC 字符串拼接改参数化查询，保留查询语义与参数类型 | 动态表名/排序、复杂ORM方言和无法证明等价的重构 |
| 路径遍历 | 在明确基目录和文件用途下加入规范化、边界与链接风险防护 | 未验证实际文件系统语义的字符串 startsWith；无法隔离的文件竞争 |
| 依赖漏洞 | 固定版本升级、依赖树对照、兼容性与安全测试 | 只改POM版本就认定完成修复，或任意跨大版本升级 |
| 其他漏洞 | 生成有根因依据的修复建议或待审核补丁 | 自动发明业务授权规则、全类RCE/反序列化通用修复 |

首个 MVP 至少完成 **一个已知版本依赖风险分析、一条源码漏洞验证，以及该源码漏洞的补丁生成和验证**。不要求第一轮同时自动修复所有类别。

### 9.3 不允许的“修复”

- 删除安全测试、关闭扫描规则、修改预期断言以掩盖问题。
- 去掉认证授权或放宽权限来让测试通过。
- 用吞异常、统一错误响应或 WAF 特征过滤代替根因修复。
- 在补丁中增加秘密、下载不明脚本、隐藏网络调用或无关业务变更。
- 覆盖原仓库未提交修改、修改不在许可范围的文件、自动发布或部署。

### 9.4 补丁状态

补丁生成状态：`proposed → generated`。

技术验证状态独立保存：`not_run / validation_pending / validated / validation_failed / inconclusive`。

交付状态另记：`not_exported / exported`；人工处置另记 `pending / accepted / rejected / applied`。导出或用户接受均不能改变技术验证结论，失败/未验证补丁导出时必须明确标注。

Patch Manifest 和报告必须保留 SourceSnapshot Hash、PatchHash、TestSuite Hash、ValidationRun、配方/环境版本及验证状态。`validated` 只针对这组明确记录的输入、测试与环境，不是全程序无漏洞证明。

## 10. 最小数据模型与产物

新业务使用如下概念，不把所有对象强行映射成旧 Mission：

| 对象 | 内容 |
|---|---|
| Project / SourceSnapshot | 来源、Commit、文件清单与 Hash、语言、允许路径 |
| Run / AgentStep | 用户目标、计划、模型/规则配置、工具调用和恢复检查点 |
| Dependency / AdvisoryMatch | 解析依据、直接/传递关系、版本命中、情报版本 |
| Hypothesis / Finding | 漏洞假设、根因、位置、状态、影响和限制 |
| Evidence | 源码引用、分析路径、依赖链、日志和测试证据 |
| FixPlan / Patch | 目标Finding、基线Hash、修改范围、Diff、PatchHash |
| ValidationRun | 环境、命令配方、前后版本、输出、退出码与结论 |
| RunPolicy / Approval | 源码读取、模型外发、修复写入和测试执行权限 |

技术选择：沿用现有 **Go + PostgreSQL**，以普通模块组织；证据和补丁存受控本地目录并记录 Hash。首版不引入图数据库、向量数据库、消息集群或新的数据库后端。

PostgreSQL 保存权威业务状态，Artifact 目录保存不可变内容。先按纵向闭环增加所需表与接口，不先实现一整套新平台 Schema。

推荐每个 Run 交付：

- `report.md`、结构化 `findings.json`。
- 依赖清单和一种固定版本的标准 SBOM 导出格式。
- `patches/<finding-id>.patch`、Patch Manifest、回归测试。
- `validation.json`、必要日志、证据索引与 Hash。
- 分析覆盖范围、跳过项、情报版本和无法确认项。

SBOM / SARIF 等格式的准确版本在导出器实现时固定并用官方 Schema 校验；内部模型不能只为某个外部格式服务。

## 11. 工具契约与权限控制

建议最小工具面：

- 项目：`inspect_project`、`list_files`、`read_source`、`search_source`、`query_symbols`。
- 供应链：`inspect_dependencies`、`match_advisories`、`trace_dependency_reachability`。
- 审计：`query_endpoints`、`trace_dataflow`、`record_hypothesis`、`record_finding`。
- 修复：`create_patch_workspace`、`apply_patch`、`inspect_diff`。
- 验证：`run_validation_recipe`、`read_validation_result`。
- 交付：`export_report`、`export_patch`、`get_run_status`。

这些是待实现的业务契约，不表示当前工具已经存在。每个工具必须定义输入/输出 Schema、错误语义、访问范围、预算单位、是否副作用、幂等策略及证据引用方式。

权限分开授予：

1. 读取本地项目。
2. 将哪些源码/片段发送给哪个模型服务。
3. 在独立副本修改哪些文件。
4. 执行哪些测试配方及是否允许网络。
5. 导出、应用、提交或发布补丁。

读取许可不自动包含外发、运行或原地修改许可。重复模型工具调用、恢复和事件重投不能绕过一次性审批或重复执行副作用。

## 12. 安全与质量底线

- 分析快照只读；修复仅限独立副本，输出可审查、可回退。
- 非可信仓库不能通过 Prompt Injection 扩权、读取宿主秘密或修改授权。
- 源码和测试输出发送模型前按项目数据策略筛选与脱敏；外发服务与地址需明确许可。
- 模型密钥由宿主受控客户端持有，不注入项目测试环境。
- 工具输出、模型解释、扫描结果、源代码证据和运行时证据分别标记。
- 测试未执行、跳过、超时、编译失败、环境缺失分别报告；退出码0也不能单独证明漏洞已修复。
- 原始证据不可覆盖；脱敏副本独立 Hash，报告默认使用脱敏内容。
- 结果含高/中/低危、触发条件、复现依据、修复方案和局限。
- 预算控制覆盖模型调用、Token/成本、工具步骤、分析时长、测试资源与磁盘；预算耗尽仍能保存结果、停止执行和导出已有产物。

## 13. 现有 P0.1 / P0.2 代码怎么处理

### 13.1 事实基线

当前已有代码是离线授权与事务基础：身份、Scope、Task/Intent/Mission/Fact、预算、Lease/Fencing、Outbox、任务成员、离线工具请求和一次性审批。

已有真实 PostgreSQL 和 Linux-race 测试证明了部分并发、事务与权限性质，但 **没有证明模型接入、供应链分析、Java AST审计、漏洞发现、补丁生成或修复正确性**。CLI `demo-offline` 不是目标产品功能演示。

### 13.2 保留 / 适配 / 暂缓

| 现有模块 | 处理 | 原因 |
|---|---|---|
| 显式迁移、checksum、事务、错误处理 | 保留 | 可支撑新Agent状态与证据一致性 |
| Scope/审批摘要/幂等/预算机制 | 按工具和工作区权限适配 | 复用安全机制，不要求每次离线审计先搭完整目标测试合同 |
| 不可变记录、Fact/证据关系思路 | 复用并补新领域对象 | 分析和补丁需要明确来源与版本 |
| Task/Intent/Mission API | 留在legacy兼容边界，按实际需要映射 | 不强迫统一Agent通过Worker领取才能使用工具 |
| 任务成员与全局角色 | 保留现状，暂停扩展 | 不以多租户IAM建设阻塞新Agent |
| Lease/Fencing/资源池 | 不删除；暂缓扩展 | 将来用于真实长时工具资源，首版不以多Worker调度为核心 |
| Outbox投递/死信 | 保留测试与实现，按需接入Run事件 | 不能为了用事件系统而引入跨Agent交接 |
| 原P0完整平台门禁清单 | 不再按原顺序推进 | 新产品先做单Agent纵向闭环，执行安全在相应工具开放前落实 |

### 13.3 迁移约束

- 本次只替换执行文档，不删除源码、迁移历史、数据库、测试或参考项目。
- 001/002/003 等已应用迁移不改写；新业务需要数据库变更时使用新迁移。
- 历史测试文档保留并标为旧路线工程记录，不再作为产品路线依据。
- 不直接把 legacy Mission/Approval 的离线成功回执当成新执行器许可。
- 若适配旧API比实现小接口更复杂，允许新模块隔离实现；通过明确ADR说明，不为“复用”牺牲主循环可理解性。

## 14. 开发路线：以可运行新 Agent 为中心

使用 **R0—R6** 区分旧平台 P0—P6，不沿用旧阶段定义。时间不作为通过依据。

### R0：产品转向与最小样本（当前文档阶段）

交付：新执行方案、README路线更新、legacy定位、源码/依赖正负样本及首个端到端验收脚本设计。

验收：所有当前入口文档都明确TRIDENT是统一安全Agent；旧平台方案不再被引用为有效架构。此阶段不等于业务能力已实现。

### R1：统一 Agent Core + 项目只读工具

交付：一个主决策循环、一个真实模型适配、工具注册与策略、Run状态/预算/恢复、快照与基础源码检索、CLI运行入口。

验收：给一个小型Java样本，Agent能自主调用工具识别项目结构、定位入口、记录有来源的假设并按证据回答；超时/取消/模型拒绝可正确结束；不能越界读取或外发未批准数据。

**R1必须尽早给出真正Agent演示，不以继续补治理表替代。** 没有外发许可时只可做假模型协议测试，并明确真实接入待验证。

### R2：供应链分析 + 有证据的源码漏洞发现

交付：Maven依赖解析、固定情报快照、SBOM、Java AST/入口/基础Source-Sink、有限跨方法路径和结果分层。

验收：样本能识别一个版本命中的依赖并解释可达性限制；定位至少一条有源码证据的漏洞；防护负例不误报为确认；未解析模块/调用列入覆盖报告。

### R3：受控验证 + 最小自动修复闭环

交付：隔离验证Runner、Patch Workspace、FixPlan、最小补丁生成、安全回归、报告与Patch导出。

验收：对一个源码漏洞，基线安全测试因该漏洞失败，补丁后同测试通过；原有正常行为测试不退化；用户原目录不变；失败补丁明确标记。将R1—R3整合为第一个可用MVP。

**不能把“生成一个Diff”算作R3完成。**

### R4：扩大依赖与审计/修复覆盖

交付：Gradle可信解析路径、更多Spring权限与Servlet入口、依赖升级验证、SSRF/上传/权限等专项规则、可配置修复策略。

验收：每一项新增能力有正例、负例、边界例和覆盖限制；未知业务授权不自动修复；框架或语言不支持时正确报告partial。

### R5：可靠性、数据治理与CI集成

交付：崩溃恢复、工具副作用对账、证据访问/保留、凭据与服务账号分权、SARIF/CI出口和可选补丁提交集成。

安全隔离、秘密保护、外发许可和副本写入不能等到R5才补；R5完善的是生产级治理，不是首次建立基本边界。

### R6：发布与生产验收

交付：固定版本与依赖、安装/部署/备份文档、可复现实验集、成本性能报告、版本兼容说明和完整验收报告。UI按实际需求后置，不做成新的多Agent SOC平台。

## 15. MVP 的可复现验收任务

准备一个仅包含合成数据的本地Java Web样本，包含：

- Maven多模块/属性依赖案例、一项已知公告的版本匹配及一项不受影响对照。
- 一条可修复的JDBC SQL注入或明确基目录的文件访问缺陷。
- 至少一条净化/参数化防护负例和一个无法解析的动态调用案例。
- 正常业务测试和安全回归测试；不含真实凭据或生产地址。

验收步骤：

1. 用户许可分析、模型外发范围、修复工作副本和固定测试配方。
2. Agent导入快照，识别项目、依赖与可分析范围。
3. 产生依赖风险分层、定位源码漏洞并给出可复核路径。
4. Agent请求并执行本地沙箱验证，记录根因与对照。
5. Agent生成FixPlan、补丁和测试，不改原项目。
6. 工具记录基线失败/补丁通过/业务回归及所有退出码。
7. 独立规则或人工复核补丁没有删除测试、放宽权限或修改无关代码。
8. 导出报告、SBOM、Diff、测试和证据索引；中断后恢复不重复应用补丁。

必须同时有至少一个失败场景：如依赖无法解析、模型不可用、补丁编译失败或验证超时。正确报告失败也是验收内容，不能只演示happy path。

## 16. 测试与指标

| 层次 | 验收重点 |
|---|---|
| 单元 | 路径规范化、JSON/工具Schema、依赖版本、AST规则、Diff范围、摘要与状态 |
| Agent协议 | 工具调用关联、分页/超大输出、取消、预算、模型截断/拒绝与错误恢复 |
| 集成 | 真实解析器、数据库、模型适配、隔离Runner、Artifact关联 |
| 对抗 | 仓库Prompt Injection、符号链接越界、恶意归档/构建、凭据外泄、补丁逃逸 |
| 漏洞质量 | 分类Precision/Recall、证据完整性、误报反证、未解析覆盖 |
| 修复质量 | 漏洞回归、正常功能、补丁最小性、依赖兼容、失败与回退 |
| 可靠性 | 中断/重试、重复调用、磁盘满、数据库断连、不确定副作用 |

指标规则：

- 基于固定版本、预先标注的数据集，分类报告Precision/Recall及样本规模；不把命中数量当准确率。
- 补丁成功率需明确分母和失败项，排除“测试未跑却算修复成功”。
- 首个MVP固定样本的必需用例全部通过；泛化准确率阈值在扩大样本后制定，不先承诺没有依据的百分比。
- 分开记录模型Token/成本、解析时间、验证时间与总时长。
- 记录工具、模型、规则、情报、JDK、依赖和容器版本，使结果可以重现。

## 19. 最终发布验收

TRIDENT只有满足以下要求才可宣称具有本方案的产品能力：

- 一个统一Agent可自主使用受控工具完成任务，不依赖三个旧项目运行。
- 明确支持范围内能分析供应链风险和源码漏洞，未知项有覆盖说明。
- Finding有证据、触发条件、影响与确认等级，不把模型猜测写成事实。
- 至少声明支持的自动修复类别能输出有效补丁和回归验证，失败项如实报告。
- 分析与补丁可追溯到同一基线；原项目不被隐式覆盖。
- 恶意仓库不能越界读写、执行宿主命令、拿到秘密或改变授权。
- 模型外发、工具执行、预算和提交/发布权限可被独立约束。
- 中断恢复不重复副作用；报告和补丁可复核、可回退。

**最终准则：吸收三个项目的优点，做成 TRIDENT 自身的智能体；分析、验证和修复是同一产品的能力闭环，不是三个 Agent 的派发平台。**
